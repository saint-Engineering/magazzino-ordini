# M6 · G4 — Esercizio: una feature attraversa tutta la pipeline

**Pomeriggio, individuale, sul tuo repository.** Stesso esercizio per tutti.
Obiettivo: comporre in una pipeline gli agenti e i controlli dei tre giorni precedenti,
far passare una feature dalla richiesta alla release in bozza e **misurare** ogni tappa.

```
richiesta → analista (VS Code) → issue dal modulo → cloud agent (sviluppatore-magazzino)
→ PR → build + CodeQL + Copilot code review → tu → merge → tag → release in bozza
```

## 1 · Monta la pipeline (su `main`)

Crea questi file (il testo è in fondo a questa pagina):

- `.github/ISSUE_TEMPLATE/feature.yml`: il modulo delle issue per il cloud agent;
- `.github/agents/analista.agent.md`: agente per VS Code che scrive le issue, sola lettura;
- `.github/agents/sviluppatore-magazzino.agent.md`: agente per il cloud agent, test prima
  del codice;
- `docs/pipeline/registro.md`: il registro da compilare.

Poi **Settings → Rules → Rulesets → New branch ruleset**, nome `main protetto`,
**Enforcement status: Active**, target **Default branch**:

| Regola | Impostazione |
|---|---|
| Restrict deletions, Block force pushes | attive |
| Require a pull request before merging | Required approvals **0** (sei da solo nel repo), **Require conversation resolution** |
| Require status checks to pass | check `build` (dal workflow di ieri) |
| Require code scanning results | CodeQL, Security alerts **High or higher** |
| Automatically request Copilot code review | attiva, con **Review new pushes** |
| Bypass list | vuota |

Prova: un push diretto su `main` deve essere rifiutato.

## 2 · Dalla richiesta alla issue

La richiesta del responsabile della logistica:

> «Quando spediamo un ordine voglio il codice di tracking del corriere, così i clienti
> sanno dov'è il pacco. I codici sono tipo IT123456789IT.»

1. In VS Code scegli l'agente **analista** e dagli la richiesta.
2. Confronta la sua issue con le regole qui sotto: cosa ha visto? cosa gli è sfuggito?
3. Crea la issue su GitHub con il modulo **Feature per il cloud agent**, con almeno:

- R1 Spedire un ordine richiede un codice di tracking: 2 lettere, 9 cifre, 2 lettere
  (es. IT123456789IT); maiuscole e minuscole indifferenti, si salva in maiuscolo.
- R2 Il codice si salva nell'ordine e si vede nel dettaglio; un ordine spedito non
  cambia più codice.
- R3 Lo stesso codice non può essere usato da due ordini.
- R4 Nel dettaglio di un ordine confermato il pulsante Spedisci ha accanto il campo del
  codice; un codice non valido mostra l'errore e l'ordine resta CONFERMATO.
- Confini per i test: 8 e 10 cifre, lettere al posto delle cifre, codice duplicato
  scritto in minuscolo.

## 3 · Il cloud agent, con il suo custom agent

**Assignees → Copilot**; nel riquadro scegli l'agente **sviluppatore-magazzino**.
Annota l'ora nel registro. Mentre lavora: quali tappe partiranno da sole sulla sua PR?

## 4 · La PR attraversa i controlli

1. **Approve and run workflows**: partono `build` e CodeQL.
2. Copilot code review arriva da sola (regola del ruleset): leggi i commenti.
3. La tua review: R1-R4, test con i confini, architettura (`git grep` sugli import),
   scope (nessun file `.github/` o `pom.xml` toccato).
4. Almeno una iterazione `@copilot`; ogni nuovo push riceve una nuova review di Copilot.
5. Merge solo con tutti i check verdi e le conversazioni risolte.

## 5 · Rilascio in bozza e misure

1. `git tag v0.2.0` e `git push origin v0.2.0`: in **Releases** la bozza con il jar.
2. Compila `docs/pipeline/registro.md` e rispondi alle tre domande del debrief.
3. Commit del registro con una PR (il ruleset non ti lascia fare push su `main`).

## Fatto quando

- il ruleset è attivo e un push diretto su `main` viene rifiutato;
- la PR del cloud agent è passata da `build`, CodeQL, Copilot code review e da te;
- R1-R4 sono verificate e i test coprono i confini;
- la release `v0.2.0` è in bozza e il registro è compilato nel repo.

## File da creare al punto 1

`.github/ISSUE_TEMPLATE/feature.yml`:

````yaml
name: Feature per il cloud agent
description: Una feature scritta perché un agente la possa implementare senza fare domande
title: "[feature] "
labels: ["feature"]
body:
  - type: markdown
    attributes:
      value: |
        Una issue per un agente non può essere ambigua: l'agente non ti fa domande.
        Scrivi regole verificabili, con i numeri di confine, e cosa NON va toccato.
  - type: textarea
    id: perche
    attributes:
      label: Perché
      description: Chi la usa e cosa ci guadagna, in una o due frasi.
      placeholder: Come magazziniere voglio ... per ...
    validations:
      required: true
  - type: textarea
    id: regole
    attributes:
      label: Regole
      description: Numerate (R1, R2, ...), verificabili, con i valori di confine.
      placeholder: |
        - R1 ...
        - R2 ...
    validations:
      required: true
  - type: textarea
    id: vincoli
    attributes:
      label: Vincoli
      description: Architettura, test, build. Rimanda ai file del repo invece di riscriverli.
      value: |
        - Rispetta .github/instructions/architettura.instructions.md.
        - Un test per ogni regola, con i confini. ./mvnw test deve essere verde.
    validations:
      required: true
  - type: textarea
    id: fuori-scope
    attributes:
      label: Fuori dallo scope
      description: Cosa l'agente non deve modificare.
    validations:
      required: true
  - type: checkboxes
    id: pronta
    attributes:
      label: Prima di assegnarla a Copilot
      options:
        - label: Ogni regola si può verificare con un test o provando l'app
          required: true
        - label: Ho scritto i valori di confine
          required: true
````

`.github/agents/analista.agent.md`:

````markdown
---
name: analista
description: Trasforma una richiesta in linguaggio naturale in una issue pronta per il cloud agent, con regole numerate, valori di confine, vincoli e fuori scope. Non modifica file.
tools: ['read', 'search']
---
Sei l'analista del repository Magazzino & Ordini. Ricevi una richiesta di una persona
del business e produci il testo di una issue che segue il modulo
`.github/ISSUE_TEMPLATE/feature.yml`: Perché, Regole, Vincoli, Fuori dallo scope.

- Leggi il codice per capire cosa esiste già: non chiedere di rifare ciò che c'è.
- Ogni regola è numerata (R1, R2, ...) e verificabile con un test o provando l'app.
- Scrivi sempre i valori di confine (minimi, massimi, formati) e i casi di errore.
- Se la richiesta è ambigua, elenca le domande da fare alla persona invece di inventare.
- Non scrivere codice e non modificare file: il tuo prodotto è il testo della issue.
````

`.github/agents/sviluppatore-magazzino.agent.md`:

````markdown
---
name: sviluppatore-magazzino
description: Implementa una issue con regole numerate, prima i test e poi il codice, rispettando l'architettura.
---
Sei lo sviluppatore del repository Magazzino & Ordini (Java 25, Spring Boot 4.1.1,
Thymeleaf, H2). Lavori da una issue scritta con il modulo "Feature per il cloud agent".

Metodo, in quest'ordine:

1. Leggi la issue ed elenca le regole R1..Rn con i loro casi di confine.
   Se una regola è ambigua scegli l'interpretazione più restrittiva e dichiaralo
   nella descrizione della PR.
2. Rispetta `.github/copilot-instructions.md` e `.github/instructions/*.instructions.md`:
   controller → service → model/repository, regole nel model, ora dal bean Clock.
3. Per ogni regola scrivi prima il test, con i valori attesi calcolati a mano dalla
   issue, poi il codice che lo fa passare.
4. Tocca solo quello che serve alla issue. Non modificare `.github/`, `pom.xml` e i
   workflow: se pensi che servano modifiche lì, scrivilo nella PR e fermati.
5. Prima di chiudere `./mvnw -B test` deve essere verde.
6. Nella descrizione della PR metti una tabella "regola → test → file" e una sezione
   "Cosa non ho fatto e perché".
````

`docs/pipeline/registro.md`:

````markdown
# Registro della pipeline (M6 · G4)

Una riga per tappa. Gli orari dalla timeline della issue e della PR; i costi da
**Settings → Billing** (AI credits e minuti di GitHub Actions) se li vedi, altrimenti
"non visibile".

| Tappa | Chi | Inizio | Fine | Esito | Intervento umano |
|---|---|---|---|---|---|
| Issue (analista + modulo) | agente analista + io | | | | |
| Implementazione | cloud agent, `sviluppatore-magazzino` | | | | |
| Build e test | Actions, job `build` | | | | |
| CodeQL | code scanning | | | | |
| Code review | Copilot | | | | |
| Iterazioni `@copilot` | cloud agent | | | | |
| Review e merge | io | | | | |
| Tag e release in bozza | Actions, job `release` | | | | |

## Domande per il debrief

1. Quale tappa ha trovato il problema più grave? Quale non ha trovato niente?
2. Dove hai dovuto intervenire tu, e la regola che ti ha costretto era scritta?
3. Questa feature valeva una pipeline di agenti, o bastava Agent in VS Code?
````
