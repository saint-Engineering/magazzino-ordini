# M7 · G3 — Esercizio: il server MCP entra nella pipeline

**Pomeriggio, individuale, sul tuo repository.** Stesso esercizio per tutti.
Obiettivo: dare al **Copilot cloud agent** il tuo server MCP, con il minimo dei permessi,
e far passare dalla pipeline del Modulo 6 una feature che lo usa.

```
issue → cloud agent (sviluppatore-magazzino) ──stdio──► java -jar … --spring.profiles.active=mcp-stdio
      → PR → build + CodeQL + Copilot code review → tu → merge
```

Parti dal tuo `main` con il server di ieri. Ogni modifica passa da una PR.

## 1 · Il server in stdio (40 min)

Il cloud agent avvia i server locali come processi e parla su stdin/stdout. La stessa
applicazione, con un profilo diverso:

1. `pom.xml`, dentro `<build>`: `<finalName>magazzino-ordini</finalName>` (il jar ha un
   nome fisso).
2. `src/main/resources/application-mcp-stdio.properties`:

   ```properties
   spring.main.web-application-type=none
   spring.main.banner-mode=off
   spring.ai.mcp.server.stdio=true
   logging.pattern.console=
   logging.file.name=target/mcp-stdio.log
   ```

   Stdout è il canale del protocollo: una sola riga di log lo romperebbe.
3. Prova in locale: `.\mvnw.cmd -DskipTests package`, poi l'Inspector in **STDIO** con
   command `java` e argomenti `-jar target/magazzino-ordini.jar --spring.profiles.active=mcp-stdio`.
   Devi vedere i quattro tool; i log stanno in `target/mcp-stdio.log`.

## 2 · Il server per il cloud agent (40 min)

1. In `.github/workflows/copilot-setup-steps.yml`, dopo il download delle dipendenze:

   ```yaml
   - name: Costruisci il jar per il server MCP
     run: ./mvnw -B -q -DskipTests package
   ```

   Lancia il workflow da **Actions → Copilot Setup Steps → Run workflow**: deve essere verde.
2. **Settings → Copilot → MCP servers**, incolla e salva:

   ```json
   {
     "mcpServers": {
       "magazzino": {
         "type": "local",
         "command": "java",
         "args": ["-jar", "target/magazzino-ordini.jar",
                  "--spring.profiles.active=mcp-stdio"],
         "tools": ["cerca_prodotti", "prodotti_sotto_scorta"]
       }
     }
   }
   ```

   `tools` è una **allowlist**: il cloud agent usa i tool senza chiederti conferma, quindi
   solo quelli di lettura che gli servono. Niente `dettaglio_ordine` (ha il nome del
   cliente) e niente `riassortisci_prodotto`.
3. Salva la stessa configurazione in `docs/mcp/cloud-agent.json` e aggiungi la scheda del
   server `magazzino` in `docs/mcp/server-ammessi.md`: le impostazioni del repo non hanno
   storia, il file sì.
4. Nel custom agent `sviluppatore-magazzino`, una riga: per i dati del catalogo usa i tool
   del server `magazzino` e riporta nella PR cosa hai letto.

## 3 · Una feature che usa il server (80 min)

Nuova issue con il modulo **Feature per il cloud agent**, titolo «Pagina delle scorte»:

- **R1** La pagina `/scorte` elenca i prodotti con giacenza uguale o inferiore alla scorta
  minima, dal più scoperto, con gli stessi dati del tool `prodotti_sotto_scorta`.
- **R2** Colonna «Mancanti» = scorta minima − giacenza, mai negativa (0 se uguale).
- **R3** Ogni riga ha il link «Riassortisci» alla pagina di riassortimento del prodotto.
- **R4** Voce «Scorte» nel menu.
- **R5** Nessun prodotto da riassortire = messaggio «Nessun prodotto da riassortire».
- Nella PR: la tabella che restituisce `prodotti_sotto_scorta` sui dati di prova e il
  confronto con quella del test della pagina.

**Assignees → Copilot**, agente **sviluppatore-magazzino**. Poi:

1. **View session** → menu **…** → **Copilot** → step **Start MCP Servers**: ci sono i
   due tool del magazzino? Se il server non parte, l'errore è qui.
2. Nei log della sessione: ha chiamato `prodotti_sotto_scorta`? Con che risultato?
3. La PR attraversa i controlli del Modulo 6 (build, CodeQL, Copilot code review, tu).
   Con i dati di prova la pagina mostra NAS-50, TAS-8 e CAC-PH2, in quest'ordine.

## 4 · La revisione della configurazione (30 min)

In fondo a `docs/mcp/server-ammessi.md` rispondi:

1. Cosa cambierebbe con `"tools": ["*"]`?
2. Se il server fosse remoto (HTTP) con un token, dove metteresti il token e come lo
   chiameresti?
3. Chi decide se gli sviluppatori dell'organizzazione possono usare server MCP in VS Code?
4. Dove vedi quali tool ha chiamato il cloud agent in una sessione?

Merge della PR con le risposte.

## Fatto quando

- il jar parte in stdio e l'Inspector vede i quattro tool;
- la configurazione MCP del repo ha solo `cerca_prodotti` e `prodotti_sotto_scorta`, e la
  sua copia è in `docs/mcp/cloud-agent.json`;
- la sessione del cloud agent mostra il server `magazzino` avviato e la PR riporta i dati
  letti con il tool;
- la PR della feature è mergiata con i controlli verdi e le quattro risposte sono nel repo.
