# M6 · G2 — Esercizio: una issue al cloud agent, una PR da rivedere

**Pomeriggio, individuale, sul tuo repository.** Stesso esercizio per tutti.
Obiettivo: far scrivere una feature al **Copilot cloud agent** partendo da una issue,
far rivedere la sua PR a **Copilot code review** e decidere tu, con le regole di
architettura alla mano, se e quando fare il merge.

Si parte dal tuo repo così com'è dopo ieri (con le istruzioni e gli sconti).

## 1 · Prepara il repo per l'agente

Crea su `main` questi due file (il contenuto è in fondo a questa pagina), commit e push:

- `.github/workflows/copilot-setup-steps.yml`: installa Java 25 e scarica le dipendenze
  Maven nell'ambiente del cloud agent, così può lanciare `./mvnw test`;
- `.github/instructions/architettura.instructions.md`: le regole di architettura, lette
  dall'agente quando scrive e da Copilot quando rivede la PR.

Su GitHub: **Actions → Copilot Setup Steps → Run workflow**: deve finire verde.

## 2 · Scrivi la issue e assegnala a Copilot

Crea una issue con titolo **Riassortimento e storico dei movimenti** e questo testo
(puoi migliorarlo, non toglierci regole):

```markdown
Come magazziniere voglio registrare la merce che arriva e vedere lo storico dei
movimenti, per sapere sempre perché una giacenza è cambiata.

## Regole
- R1 Nella pagina Prodotti ogni riga ha il link "Riassortisci" che apre
  /prodotti/{codice}/riassortimento.
- R2 Il form chiede i pezzi arrivati (intero da 1 a 1000) e una nota facoltativa
  (al massimo 200 caratteri).
- R3 Se i dati non sono validi la pagina mostra l'errore e la giacenza non cambia.
- R4 Ogni riassortimento registra un movimento: data e ora, prodotto, tipo CARICO,
  pezzi, nota.
- R5 Anche gli ordini registrano movimenti: uno SCARICO per riga quando l'ordine
  viene creato, un RESO per riga quando viene annullato, con il numero d'ordine.
- R6 La pagina /movimenti elenca i movimenti dal più recente; il menu ha la voce
  "Movimenti".

## Vincoli
- Rispetta .github/instructions/architettura.instructions.md: i controller non
  usano i repository, le regole stanno in model e service.
- L'ora si prende dal bean Clock, mai da LocalDateTime.now() senza argomenti.
- Test per ogni regola, con i confini (0, 1, 1000, 1001 pezzi; nota di 200 e 201
  caratteri). ./mvnw test deve essere verde.

## Fuori dallo scope
- Nessuna modifica a sconti, spedizione e stati dell'ordine.
```

Poi **Assignees → Copilot** e conferma. Annota l'ora: ti servirà per il registro.

## 3 · Mentre l'agente lavora

Apri la scheda **Agents** (o il link "View session" nella PR) e segui il log. Prepara
la tua revisione: sul foglio scrivi le tre cose che controllerai per prime.

## 4 · Revisione della PR

1. Leggi la descrizione della PR e il diff, file per file.
2. **Reviewers → Copilot**: richiedi la code review. Leggi i commenti: quali sono giusti?
   quali no? quale problema non ha visto?
3. Controlla a mano l'architettura: nessun `import ...repository` dentro `web`, nessuna
   regola nei controller o nei template, `Clock` usato per l'ora.
4. Prova la feature: `git fetch` e checkout del branch `copilot/...`, `.\mvnw.cmd test`,
   avvia l'app, riassortisci con 0, 1 e 1001 pezzi.
5. Almeno **una iterazione**: scrivi un commento nella PR che inizia con `@copilot` e
   chiede una correzione precisa. Aspetta il nuovo commit e ricontrolla.
6. I workflow sulle PR dell'agente partono solo dopo il tuo **Approve and run workflows**.

## 5 · Decisione e registro

Fai il merge solo se tutte le regole R1-R6 sono rispettate. Nella PR lascia un ultimo
commento con il registro:

| Voce | Valore |
|---|---|
| Ora di assegnazione / PR pronta / merge | |
| Iterazioni con `@copilot` | |
| Commenti di Copilot code review utili / sbagliati | |
| Problemi trovati solo da te | |

## Fatto quando

- `copilot-setup-steps` è verde su GitHub;
- la PR del cloud agent ha avuto la review di Copilot e almeno una iterazione `@copilot`;
- prima del merge `.\mvnw.cmd test` è verde e R1-R6 sono verificate a mano;
- il registro è nell'ultimo commento della PR.

## File da creare al punto 1

`.github/workflows/copilot-setup-steps.yml` (deve stare su `main`):

```yaml
# Prepara l'ambiente del Copilot cloud agent prima che inizi a lavorare:
# Java 25 e dipendenze Maven già scaricate, così l'agente può lanciare ./mvnw test.
# Deve stare sul branch principale; il job DEVE chiamarsi copilot-setup-steps.
name: "Copilot Setup Steps"

on:
  workflow_dispatch:
  push:
    paths:
      - .github/workflows/copilot-setup-steps.yml
  pull_request:
    paths:
      - .github/workflows/copilot-setup-steps.yml

jobs:
  copilot-setup-steps:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: "25"
          cache: maven
      - name: Scarica le dipendenze Maven
        run: ./mvnw -B -q dependency:go-offline
```

`.github/instructions/architettura.instructions.md`:

````markdown
---
applyTo: "src/main/java/**"
description: "Regole di architettura da rispettare quando si scrive codice e da controllare in review"
---
# Architettura

Dipendenze ammesse tra i package di `com.epicode.magazzino`:

- `web` → `service`, `model`. **Mai** `repository`: un controller non apre il database.
- `service` → `model`, `repository`. Un metodo pubblico = un caso d'uso `@Transactional`.
- `model` → nessun altro package dell'applicazione, niente Spring MVC.
- `repository` → `model`. Solo interfacce Spring Data, nessuna logica.

Regole:
- Le regole di business stanno nel `model`; i service le orchestrano; controller e
  template non decidono nulla.
- L'ora corrente arriva dal bean `Clock` (`LocalDateTime.now(clock)`), mai da
  `LocalDateTime.now()` senza argomenti: altrimenti i test non la controllano.
- Errori di dominio: sottoclassi di `MagazzinoException`, messaggio in italiano.

In review segnala sempre:
- un `import com.epicode.magazzino.repository` dentro `web`;
- un `if` con una regola di business dentro un controller o un template;
- una regola nuova senza un test che ne copra i confini.
````
