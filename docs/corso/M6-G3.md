# M6 · G3 — Esercizio: le falle del fornitore, gli scanner e una release in bozza

**Pomeriggio, individuale, sul tuo repository.** Stesso esercizio per tutti.
Obiettivo: far trovare le vulnerabilità agli strumenti di GitHub, correggerle con l'aiuto
di Copilot **dimostrando ogni correzione con un test d'attacco**, e far preparare
all'agente una release in bozza. Il deploy vero è al Modulo 8.

## 1 · Accendi la sicurezza del repo

**Settings → Advanced Security** (sezione "Security and quality"; il repo deve essere pubblico):

- Dependency graph, **Dependabot alerts**, **Dependabot security updates**;
- **Code scanning → CodeQL analysis → Set up → Default** (lingue: Java/Kotlin, Actions);
- **Secret Protection** / secret scanning e **push protection**;
- **Private vulnerability reporting**.

Poi aggiungi su `main` `.github/dependabot.yml` e `SECURITY.md` (testo in fondo a
questa pagina): il registro delle vulnerabilità lo compili tu nei punti 3 e 4.

## 2 · Il codice del fornitore

Un fornitore ha consegnato il modulo report ed è già "in produzione": lo aggiungi su
`main` così com'è, con un commit `Modulo report del fornitore`.

1. In `pom.xml`, dentro `<dependencies>`:

```xml
<!-- Aggiunta dal fornitore del modulo report -->
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-text</artifactId>
    <version>1.9</version>
</dependency>
```

2. `src/main/java/com/epicode/magazzino/web/ReportController.java`:

```java
package com.epicode.magazzino.web;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import org.apache.commons.text.StringSubstitutor;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.ResponseBody;

/**
 * Modulo report consegnato dal fornitore esterno.
 * Funziona, ma nessuno lo ha mai rivisto.
 */
@Controller
@RequestMapping("/report")
public class ReportController {

    // Credenziali del server FTP del fornitore, per l'invio notturno dei report
    private static final String FTP_UTENTE = "magazzino";
    private static final String FTP_PASSWORD = "Fornitore2026!";

    private final JdbcTemplate jdbc;

    public ReportController(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    /** Ordini di un cliente: /report/ordini?cliente=Rossi */
    @GetMapping("/ordini")
    public String ordini(@RequestParam String cliente, Model model) {
        String sql = "SELECT id, cliente, stato FROM ordini WHERE cliente = '" + cliente + "'";
        model.addAttribute("righe", jdbc.queryForList(sql));
        model.addAttribute("titolo", "Ordini di <b>" + cliente + "</b>");
        return "report";
    }

    /** Scarica un report già generato: /report/file?nome=ordini-ottobre.csv */
    @GetMapping("/file")
    @ResponseBody
    public byte[] file(@RequestParam String nome) throws IOException {
        return Files.readAllBytes(Path.of("report", nome));
    }

    /** Intestazione con segnaposto: /report/intestazione?modello=Report del ${date:dd/MM/yyyy} */
    @GetMapping("/intestazione")
    @ResponseBody
    public String intestazione(@RequestParam String modello) {
        return StringSubstitutor.createInterpolator().replace(modello);
    }

    String credenzialiFtp() {
        return FTP_UTENTE + ":" + FTP_PASSWORD;
    }
}
```

3. `src/main/resources/templates/report.html`:

```html
<!DOCTYPE html>
<html xmlns:th="http://www.thymeleaf.org" lang="it">
<head th:replace="~{fragments :: head('Report')}"></head>
<body>
<header th:replace="~{fragments :: menu}"></header>
<main>
    <h1 th:utext="${titolo}">Report</h1>
    <table>
        <thead>
        <tr>
            <th>N.</th>
            <th>Cliente</th>
            <th>Stato</th>
        </tr>
        </thead>
        <tbody>
        <tr th:each="r : ${righe}">
            <td th:text="${r['ID']}">1</td>
            <td th:text="${r['CLIENTE']}">Rossi</td>
            <td th:text="${r['STATO']}">CONFERMATO</td>
        </tr>
        </tbody>
    </table>
</main>
</body>
</html>
```

4. `report/ordini-ottobre.csv` (nella radice del progetto):

```
ordine;cliente;stato
1;Ferramenta Bianchi;CONFERMATO
```

Avvia l'app e prova gli attacchi (dal browser):

| Attacco | Indirizzo | Cosa succede |
|---|---|---|
| SQL injection | `/report/ordini?cliente=' OR '1'='1` | escono gli ordini di tutti |
| XSS | `/report/ordini?cliente=<i>ciao</i>` | il nome diventa HTML |
| Path traversal | `/report/file?nome=../pom.xml` | scarichi il pom del progetto |
| Interpolazione | `/report/intestazione?modello=${sys:user.home}` | esce la tua cartella utente |

## 3 · Cosa trovano gli scanner

Dopo il push aspetta la prima analisi (Actions → CodeQL) e apri la scheda **Security and quality** (si chiamava Security):

- **Code scanning**: quali alert ci sono? Per ognuno: file, riga, regola, gravità.
- **Dependabot**: l'alert su `commons-text` (CVE-2022-42889) e la PR di security update.
- Copia in `SECURITY.md` una riga del registro per ogni vulnerabilità **trovata da uno
  strumento** e una per ogni vulnerabilità **trovata solo da te** (la password FTP?).

## 4 · Correggi, con un test d'attacco per ogni falla

Per ogni alert: **Generate fix** (Copilot Autofix) oppure Agent in VS Code, ma
**prima** scrivi il test che riproduce l'attacco e lo vedi rosso, **poi** correggi e lo
vedi verde. Lavora su un branch `fix/report` e apri una PR verso `main`.

- V1 SQL injection → query del repository, niente SQL concatenato;
- V2 XSS → `th:text`, nessun HTML costruito in Java;
- V3 path traversal → solo nomi semplici `.csv`, controllo che il file stia nella cartella;
- V4 interpolazione → niente `StringSubstitutor` sull'input; via la dipendenza o 1.10.0+;
- V5 password nel codice → via dal codice;
- V6 `JdbcTemplate` nel controller → un service (regole di ieri).

Alla fine il CodeQL della PR non deve avere alert nuovi e quelli su `main` si chiudono
dopo il merge.

## 5 · Pre-deploy: la release in bozza

Chiedi all'agente (Agent in VS Code o cloud agent con una issue) un workflow
`.github/workflows/build.yml` che:

- su push e pull request verso `main` compila e lancia i test (`./mvnw -B verify`);
- su un tag `v*` crea una **release in bozza** con le note generate e il jar allegato.

Rivedi il workflow riga per riga (permessi minimi!), poi `git tag v0.1.0` e
`git push origin v0.1.0`: in **Releases** deve comparire la bozza. **Non pubblicarla.**

## Fatto quando

- code scanning, Dependabot e secret scanning sono attivi;
- per ogni vulnerabilità V1-V6 c'è una riga nel registro di `SECURITY.md` e, per V1-V4,
  un test d'attacco verde;
- la PR `fix/report` è mergiata senza alert nuovi di CodeQL;
- la release `v0.1.0` è in bozza con il jar allegato.

## File del punto 1

`.github/dependabot.yml`:

```yaml
# Aggiornamenti di versione: Dependabot apre una PR a settimana per le dipendenze
# Maven e per le action dei workflow. Gli aggiornamenti di sicurezza (security updates)
# si attivano a parte, in Settings → Advanced Security.
version: 2
updates:
  - package-ecosystem: "maven"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

`SECURITY.md`:

````markdown
# Sicurezza

## Segnalare una vulnerabilità

Non aprire una issue pubblica. Usa **Security and quality → Report a vulnerability** di
questo repository (private vulnerability reporting).

## Cosa controlliamo in automatico

- **CodeQL** (code scanning, default setup) su ogni push e pull request verso `main`.
- **Dependabot**: alert e PR di sicurezza, PR settimanali di aggiornamento.
- **Secret scanning** con push protection.

| Id | Dove | Problema | Trovata da | Correzione | Test d'attacco |

````
